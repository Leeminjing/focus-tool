# 研究设计

日期：2026-10-27。目标是降低完成正确任务的总时间，同时降低无效执行量。具体性能数字由实验产生，不预设 Go、集中队列或更多并发一定更快。

## 研究问题与边界

将问题分成三条独立轴：

1. 调用何时就绪：完整模型响应后、单个调用校验后、依赖结果绑定后。
2. 执行何时开始：就绪后等待资源、工作区锁和权限准入的时间。
3. 结果何时影响决策：工具完成后，投递、消费、决策和后续行动之间的延迟。

M1 只研究第 3 条，同时测量取消确认。Go 标准库用于本地进程与并发原语，调度逻辑由本仓库实现。选择 Go 是实验实现选择，未做语言性能比较。源码读取使用网络，实验运行不访问网络或模型服务。

Focus 普通工具回合已有并发；主要对照组应是并发等齐。源码依据见 [协议研究](protocol-research.md)。

## 标准架构与验收范围

用户明确将下图纳入本会话首条需求，作为完整研发目标和架构验收标准。M1 是其中的首个局部实验；现在已在独立仓库中实现图中全部模块的本地闭环，真实 Focus 部署仍需要接入其现有治理与消息边界。

![工具运行时标准架构图](images/tool-runtime-original.png)

按图形成闭环：Context A／B 的 Run → Focus 工具适配层 → 自研统一调度器 → Python／本地进程执行器 → 结果事件与归属路由 → 对应 Run。结果路由直接面向所属 Run；消息配对、唤醒和消费确认在相应模块内部落实，不新增图外的强制中转节点。运行时集中管理工具任务，Run 根据已消费结果决定继续、重规划或取消工作。

### 模块职责与当前状态

| 模块 | 目标职责 | 当前状态 |
|---|---|---|
| Context Run | 消费所属结果、更新计划、提交后续任务或取消请求 | `python/focus_tool/client.py` 的 Run；多 Context、版本更新、关闭、checkpoint 后 ack |
| Focus 工具适配层 | 将 Run 的工具调用转换为统一任务，维护调用身份映射并衔接权限与工作区准入 | `python/focus_tool/adapter.py`；接收 dict／AIMessage.tool_calls，稳定身份、注册工具和实际执行前回调；尚未部署到 Focus 主仓 |
| 自研统一调度器 | 跨 Context 有界队列、依赖、资源约束、公平性、背压及取消协调 | `runtime/engine.go`；按 Run 轮转、同 Context 单活动 Run、依赖绑定、读写资源、任务和未消费结果背压 |

| 本地进程执行器 | 启动进程、采集输出、等待退出、确认取消并释放执行槽 | `runtime/process.go`；直接叶子进程、超时、输出限额、stderr 错误信息与 Wait 后取消确认 |
| 结果事件与归属路由 | 将 A、B 的执行事实分别投递到所属 Run，支持结果消费与恢复 | Engine 的事件日志／Pending、stdio 事件泵、Python 按 owner 分发；顺序 ack、未消费重投及崩溃 unknown 处理 |

### 完成事件如何进入下一次决策

以下工程约束已在本地闭环中落实。运行时持久化执行状态与消费水位；实际 Focus 的 checkpoint 事务与现有 ledger 由接入方衔接，不改变标准图中的模块拓扑。

1. **提交并登记身份。** 适配层将模型调用身份关联至后台 job／attempt 和所属 Context、Run。`submit_job` 的 accepted 只完成提交调用的消息配对，后台执行保持独立账本。
2. **执行并记录真实终态。** 调度器在真正启动时要求适配层复核权限和工作区租约；执行器回报完成、失败或确认取消。运行时保留终态事实，即使对应计划已经失效。
3. **路由到对应 Run。** 结果路由按 Context／Run 归属投递完成事件。投递身份必须包含事件、执行 attempt 和接收者，不能仅依靠结果正文中的 Context 名称路由。
4. **确认是否可供决策使用。** Run 的结果接收边界检查归属、任务前提与输入版本，并去重。失效或重复事件仍保留审计记录，但不再次触发决策动作；其他 Context 的结果不能混入当前输入。
5. **保存输入并安排唤醒。** 可消费事件先进入耐久 inbox，再合并唤醒请求。空闲或等待事件的 Context 可恢复；正在执行模型调用的 Context 在下一输入边界消费。确需中止旧推理时，须取消并使旧 epoch 失去提交权。
6. **按 checkpoint 确认消费。** Run 将事件写入明确的决策输入并耐久保存 checkpoint 后，才向路由端确认该接收者已消费的水位。收到事件、写入 inbox 和决策消费分别记账；崩溃重投依靠稳定身份去重。

完成事件不能作为同一个 call ID 的第二条 ToolMessage。后台执行事实的登记也不等待模型消费：取消、执行槽和冲突资源的释放以实际退出或清理确认决定。Run 已结束时，需按明确策略继续、转移或取消任务，并更新结果接收归属。

## M1 已实现的合同

`Task = (context_id, revision, task_id, command)`。任务立即登记 queued；取得执行槽后启动进程。终态为 completed / failed / cancelled。Cancel 是请求，只有未启动或直接子进程已经 Wait 回收才产生 cancelled。完成和取消竞态允许出现“已请求取消但执行成功”，以实际退出结果记账。

工具完成记录和决策消费分开。Trace 包含 queued、started、first_output、终态、delivered、consumed_*、decision、cancel_requested，使用同一单调时钟。Done 每个任务仅返回一个终态。进程占用槽一直保留到任务退出。

Inbox 由单个控制器拥有，按 Context 核验版本并对 `(context_id, revision, task_id)` 去重。M1 中计划 1 的扫描已明确失效，因而采用保守的整版本拒收。真实系统应按任务输入和前提判定兼容性，避免每次重规划都抛弃仍有效的结果。

M1 控制器明确知道检查工具决定方向；它在等待该检查结果时允许扫描独立运行。这验证提前反馈的因果链，尚非通用“任意事件到达即评估”的调度循环。修复可以与只读扫描的停止过程重叠：扫描读取固定 corpus，修复写独立文件，没有冲突写入。

Runner 只限制同时执行的直接子进程数，未提供跨 Context 公平性，也不保证 goroutine 等待槽的 FIFO 顺序。有限批次实验中的每个提交对应一个等待 goroutine；未来集中调度必须改成显式有界队列与背压。

## M1 验收与指标

- 每种模式最后都读回修复后的有效配置；基线扫描应完成全部固定遍数并产生摘要。
- 事件模式的决策发生在请求取消之前；扫描迟到终态不参与新计划；重复完成事件不二次触发动作。
- 取消运行中的真实子进程后，必须能重新取得执行槽；取消排队任务不能启动进程。
- 同时启动数不能超过上限。只记录单调时钟耗时，不依靠绝对毫秒阈值判断正确性。

指标：trial 开始至修复及扫描均结算的总耗时、决策时间、check 完成至消费的滞后、scan 启动至终态的占用时长、取消请求至确认的耗时。扫描占用是进程墙钟时间，**不是 CPU 用量**。M1 不测模型推理成本或真实任务成功率。

## Focus 接入所需设计

不能直接把长工具的返回替换为 accepted。应显式暴露 submit_job 语义，后台执行另有身份与账本；完成事件需要收件箱、唤醒器及恢复边界。每 Context 的决策提交者必须唯一，旧推理通过 epoch 检查失去发布新任务的权利。

真正执行前复核权限和工作区租约；取消后等待实际清理，保留已发生副作用。Windows 通用 Shell 要控制进程树，当前叶子进程实验不能代替这项验证。既有 Run 结束时后台任务应继续、转移、取消或阻止结算，必须在接入前确定。
