# 短工具开销：阶段测量与下一项优化

日期：2026-10-28。接续 `860d5f3b`；本轮实现可选追踪和独立基准，未加入 worker 池、批量 WAL fsync 或后台压缩。方法、边界和时钟约束见 [测量合同](short-tools-method.md)。

**下一项优化选择有界 Python worker 池。** 这里的主要重复成本是解释器／worker 启动和导入；压缩导致的跨 Context 尾延迟也已确认，仍是独立待优化项。本轮没有把优化候选解释为已经测出的收益。

## 数据与运行条件

Windows 11、Go 1.26.5、Python 3.12.10。正式基准未与本仓测试、构建或其他实验并行；机器其他应用负载未固定。每轮先预热 24 次工具，再测 240 次读文件／搜索／JSON 解析。1／4 Context × 64 KiB／8 MiB WAL 段目标，共三轮，轮换顺序：**12 个主试验、2,880 次测量、54 次实际压缩**。另有六个追踪开关试验，共 720 次测量；包含预热时一共执行 4,032 次真实 Python 叶子工具。

全局执行与在途上限均为 4；单 Context 深度 4，四 Context 各深度 1。单／多 Context 的消费者并行程度因此也不同，不把比较解释为纯锁开销。主矩阵每轮的文件、工具输入和读回核验的最终 aggregate 相同：`read=532480, search=20480, parse=2611200`。每条 WAL 仍单独 fsync；消费者先 fsync checkpoint，再 fsync 实际 aggregate 更新，最后 ack。准入包含真实注册核对和本地工作区回调，**未测量生产 Focus 的权限／租约／数据库成本**。

以下分位数表均是“三轮各自分位数的中位数”，每轮 240 样本，nearest-rank；不是把三个 p99 合成为一个总体 p99。原始摘要保留每轮完整分布与样本数。

| Context | WAL 段目标 | 吞吐中位数（次/秒） | 提交至 ack p50 ms | p95 ms | p99 ms |
|---:|---:|---:|---:|---:|---:|
| 1 | 64 KiB | 19.74 | 191.29 | 272.11 | 398.65 |
| 1 | 8 MiB | 20.74 | 186.87 | 230.41 | 245.18 |
| 4 | 64 KiB | 18.43 | 187.89 | 388.54 | 439.05 |
| 4 | 8 MiB | 20.30 | 194.43 | 225.65 | 340.62 |

64 KiB 每轮实际压缩 9 次，8 MiB 每轮为 0；两者的 fsync 确认语义相同。吞吐跨轮波动明显，例如四 Context／8 MiB 为 20.30、21.12、17.09 次/秒，不能据三轮声称统计显著性或可外推的稳定提速。

## 开销花在哪里

下表是四 Context 下“三轮各阶段均值的中位数”，单位 ms。阶段拆分使用真实 durable 端点，旧 StartedNS／FinishedNS 的含义没有被重新命名成其他边界。

| 阶段 | 64 KiB | 8 MiB |
|---|---:|---:|
| 客户端提交 → 接收帧 fsync 完成 | 5.65 | 2.72 |
| 接收耐久 → 分配执行槽 | 1.16 | 0.28 |
| 分配执行槽 → 开始准入（含 running 落盘） | 3.95 | 0.73 |
| 注册／工作区准入往返 | 2.95 | 2.35 |
| 准入完成 → 请求启动进程 | 0.03 | 0.04 |
| 请求启动进程 → 工具函数开始 | **159.52** | **160.09** |
| 工具函数本体 | **0.22** | **0.22** |
| 函数结束 → 完成结果 fsync | 24.66 | 17.18 |
| 完成结果耐久 → Run 消费 | 8.07 | 1.57 |
| 消费 → checkpoint、实际后续写入、ack 完成 | 10.74 | 9.21 |

上述均值中位数不应相加推导分位数或精确比例。完整链路包含控制器工作，不能把完整时延减去工具本体就全部称为 Go runtime 开销。

进一步拆开启动路径：四 Context／8 MiB 的 `Cmd.Start` API 均值约 4.56 ms，worker 脚本入口到解析调用（主要是标准库初始化）约 100.00 ms，目标模块 import／函数查找约 0.85 ms；剩余包括解释器进入脚本前的启动及交接。它们是启动区间的子项，**不能再与父区间重复相加**。每任务四次 WAL fsync 合计的阶段均值约 4.11 ms；这个值**不包括压缩中 canonical 索引文件的同步写入**。

三种工具均出现相同的数量级差距。四 Context／8 MiB 的 p50 汇总如下：

| 工具 | 启动至函数开始 ms | 本体 ms | 提交至 ack ms |
|---|---:|---:|---:|
| 读文件 | 155.07 | 0.171 | 191.36 |
| 文本搜索 | 154.09 | 0.195 | 191.75 |
| JSON 解析 | 158.31 | 0.268 | 201.14 |

## 压缩确实影响其他 Context

四 Context／64 KiB 中，压缩耗时每轮 p95 分别为 **269.35、248.73、244.51 ms**；包含压缩的 Engine 持锁区间 p95 为 **270.60、250.89、246.07 ms**，普通持锁区间 p95 为 **2.23、2.77、1.71 ms**。

原始区间还记录到：

- 三轮共 **12 段**可归属其他 Context 压缩的互斥锁等待，最长重叠 **269.35 ms**。
- **7 段**请求已完成管道写入、但尚未进入服务端 handler 的等待，与其他 Context 的压缩重叠，最长 **261.81 ms**。只测 Engine.mu 等待会漏掉这一层。
- submit RTT 的每轮 p95：不与压缩重叠时为 8.37／8.11／5.97 ms；重叠时为 273.50／251.24／210.58 ms。后者每轮仅 4／5／6 个样本，必须连同样本数解读。

这些计数是不同边界的观察量，不能相加当成唯一受影响任务数；任务总时延与压缩的重叠只是关联，锁等待中的实际重叠则记录了明确不可取得锁的区间。工具结束到耐久后续行动的 p95，四 Context 小段／大段汇总分别为 **214.67／42.58 ms**。

## 追踪扰动与时钟限制

独立的 120 次任务控制使用同样的四 Context、8 MiB、fsync 和最终产物，每轮交替详细追踪开／关。共同的 job／window 记录始终保留。

| 轮次 | 关闭详细追踪（次/秒） | 开启（次/秒） | 吞吐相对差 |
|---:|---:|---:|---:|
| 1 | 18.33 | 18.42 | +0.45% |
| 2 | 19.82 | 19.40 | −2.08% |
| 3 | 19.01 | 18.50 | −2.64% |

这估计的是当前实现上的增量追踪扰动，不是旧提交与新提交的严格对照，也不是追踪开销为零的证明。尾延迟控制也有波动，详见原始摘要。

端到端及各进程内 duration 使用单调时钟；跨进程阶段关联使用同主机 Unix 时间戳。客户端 wall−monotonic 残差观测范围为 **−4.975 至 +4.784 ms**，因此不把亚毫秒跨进程间隔当成高精度结论。59 个 drain 结束→handler 开始的负间隔（可能为处理／drain 重叠或时钟配对误差）被完整计入 signed gap／重叠统计，没有静默剔除“快样本”。

## 下一项只做 worker 复用

选择依据是重复出现的约 160 ms 启动路径，相比约 0.22 ms 本体和单独报告的 WAL fsync 合计更大；这在三种真实短工具和两种压缩配置下都存在。压缩尾延迟是另一条已验证的问题，worker 池不会自动解决它。

下一轮实现限定为可信、明确允许复用的工具；有界 worker 每次只执行一个任务，每次重新核对权限／租约，固定工作区边界。取消／故障必须等待 worker 实际退出后再释放资源、重建；测试异常、输出限额、模块状态、cwd 与后续调用污染，保留当前单次子进程模式作对照。任意 Python 代码的全局状态隔离不能仅靠“重置几个变量”来承诺。

本轮**没有给出 worker 池的预期加速比例**。复用后可能转而暴露存储或压缩瓶颈，需下一轮同输入、并发上限、最终产物和持久语义的测量。随后再做 Patrol 激活与逻辑任务生命周期分离、跨 Run 结果桥接及两个断连恢复边界；当前 Run.close 的取消／archive 契约未改变。
