# 有界 Python worker 池：实现与同负载对照

日期：2026-10-28。Windows 11、Go 1.26.5、Python 3.12.10；仅本地 Go／Python 标准库、确定性控制器，无模型调用。默认新进程模式保留，复用需可信工具登记与运行时配置共同开启。实现契约见 [worker 池说明](python-pool.md)。

本轮结果支持：对这些真实短工具，复用解释器显著减少端到端等待。它没有消除首次启动、权限复核、结果落盘、checkpoint、ack 或压缩开销，不能外推为完整 Agent 的加速比例。

## 输入、测量范围与原始记录

基准独占运行，没有与测试、其他实验并行。采用同一读文件、文本搜索、JSON 解析工具，两个模式都可信登记为 `reuse=True`，仅改变运行时池大小：fresh 为 0，pool 为 4。全局并发上限均为 4，逐次 WAL fsync、执行前权限回调、consumer checkpoint、耐久后续动作及 ack 均保留；两组每轮都读回核验相同最终产物。

主对照为 1／4 Context × 64 KiB／8 MiB WAL 段 × fresh／pool，交错运行三轮，共 24 个 trial。每 trial 先预热 24 次，再测量 240 次；追踪控制为两模式各三组开／关配对，每 trial 120 次测量。总计 **7200 次测量调用，加 864 次预热，共 8064 次真实成功工具调用**。这不是长时常驻内存验收；历史保留策略的万次实验仍见 [此前记录](retention-results.md)。

- [由全部原始轨迹重算的阶段、分位数、压缩与锁等待](../results/python-pool-2026-10-28/summary.json)
- [原始数据目录：66 个 gzip JSONL 文件](../results/python-pool-2026-10-28)

每轮都有明确测量窗口；主对照共发生 **120 次真实压缩**，均在 64 KiB 组，8 MiB 组此有限窗口没有压缩。编译、生成输入、最终压缩轨迹不计入 trial。稳态从预热结束计到全部测量任务的 checkpoint／动作／ack 完成。另记录启动到实际 runtime shutdown 的完整生命周期，包含预热、测量和清理，未把闲置 worker 留在计时之外。

## 稳态端到端结果

下表每格是三轮相应指标的中位数。每轮分位数用 nearest-rank；没有将各轮混成一个分布，也没有据三轮样本声称统计显著性。端到端为客户端高分辨率单调时钟的“提交开始 → 结果消费 → checkpoint／耐久动作 → ack 完成”。

| Context | WAL 段 | 模式 | 吞吐（次/秒） | p50 ms | p95 ms | p99 ms |

| 1 | 64 KiB | fresh | 17.65 | 198.024 | 393.701 | 435.234 |
| 1 | 64 KiB | pool | 91.78 | 26.864 | 129.996 | 152.024 |
| 1 | 8 MiB | fresh | 18.10 | 211.280 | 262.233 | 298.434 |

例如四 Context／8 MiB 组，提交到结果消费的 p50／p95／p99 分别从 **241.579／303.922／337.092 ms** 降到 **8.386／11.736／13.668 ms**；完整消费与持久确认后的端到端数值见上表。按相同工具测量的函数本体仍很短，减少的是重复解释器启动与运行时初始化成本。

各轮吞吐仍有波动，尤其小段组。四 Context／64 KiB pooled 三轮压缩 p95 分别为 **131.44／148.71／169.20 ms**；复用后的端到端尾延迟仍明显高于本窗口无压缩组。原始分析同时保留压缩重叠、持锁与其他 Context 等待分布，不能只用两组吞吐差认定其全部因果。

## 确实复用、冷启动与完整清理

每个主对照 runtime 执行 264 次（24 预热＋240 测量）。fresh 启动 **264 个进程**；pool 启动 **4 个 worker**，完成 264 次，其中 260 次复用。每个 pool 主 trial 的 `peak_live=4`，关闭返回 `live=0`、`reserved=0`、`retired=4`。全部 pooled trial（含控制组）共执行 4032 次调用、启动 72 个 worker；fresh 同样执行 4032 次，每次启动一个进程。以启动事件／计数为依据，不能仅以可回收的 PID 去重估算启动次数。

默认每 worker 256 次成功调用后回收，本轮每个 worker 约 66 次，性能窗口未触发该上限；强制回收另由边界测试覆盖。

| Context／段 | 模式 | 冷调用 p50 ms | 预热总时长 s | 完整生命周期 s |
|---|---|---:|---:|---:|
| 1／64 KiB | fresh | 185.92 | 1.299 | 14.984 |
| 1／64 KiB | pool | 172.12 | 0.326 | 2.963 |
| 1／8 MiB | fresh | 211.46 | 1.375 | 14.665 |
| 1／8 MiB | pool | 191.57 | 0.325 | 1.488 |
| 4／64 KiB | fresh | 217.56 | 1.464 | 16.511 |
| 4／64 KiB | pool | 209.84 | 0.320 | 2.774 |
| 4／8 MiB | fresh | 220.29 | 1.446 | 16.355 |
| 4／8 MiB | pool | 176.52 | 0.285 | 1.289 |

也是各轮相应指标的中位数。冷调用使用预热中的首次非复用 `python_call`：fresh 每轮 24 个，pool 每轮 4 个；这是 Go 父调用跨度，包含启动至函数返回，未混入稳态。冷启动没有消失，收益来自摊销。完整生命周期包含实际关闭和回收；它不是 240 次测量吞吐的分母。

## 追踪控制与时钟限制

四 Context／8 MiB 的独立控制组每组测量 120 次，吞吐如下（三轮原值，次/秒）：

| 模式 | 追踪关 | 追踪开 |
|---|---|---|
| fresh | 16.91／19.28／19.27 | 16.01／17.09／18.75 |
| pool | 231.74／215.75／212.57 | 236.52／247.03／241.47 |

这组样本有机器负载与顺序波动，部分追踪开组反而更快，不能声称诊断零成本。主对照两臂同样开启追踪；控制组输入数量少一半，不与主组混合。

采集后首次分析遇到一个计时假设错误：短 Go 父跨度可能量化为 0，而 Python `perf_counter_ns` 能测得亚毫秒函数体，导致“父跨度减函数体”出现负数。核对本机 Go 1.26.5 Windows `runtime` 的时钟实现后，分析器改为保留该差的符号、负值计数和最小值；主对照有 **12 个负差，最小 −0.256 ms**。它们是分辨率诊断，不能当作精确非工具开销。跨进程 wall 差同样保留有符号值，不能静默裁零。比较速度使用同一 Python 客户端的高分辨率单调时钟端到端跨度。

这只修改了后处理，采集数据、runtime、工作负载、输入和原始源码指纹均未改写。采集当时的分析器保存在 [analysis-at-collection.py](../results/python-pool-2026-10-28/analysis-at-collection.py)，其 LF 规范化 SHA-256 与 `report.json` 相符（`4813199277914622b7aa0a5c077cef6d9afdf3a0ebb3a6110194ac011db018db`）；它保留原先会失败的假设。当前重算使用的分析器指纹独立写在 `summary.json` 的 `analysis_source_sha256_lf_normalized`。不删除负值、不补造样本，也不将旧分析器误称为最终版本。

## 正确性与实际 Focus 回归

本机 [完整验证记录](../results/python-pool-verification-2026-10-28.json) 的五个步骤全部通过：`go test ./...`、`go vet ./...`、Python **26 项**测试、完整架构 Demo、固定源码真实 Focus 三例。分析修正后两项分析测试另行通过；真实 Focus 再以 [池模式](../results/python-pool-focus-reuse-2026-10-28.json) 通过允许执行、权限撤销、租约释放，并断言最终 worker 池清空。两种模式均使用既有 Focus 环境和临时独立 PostgreSQL 容器，未修改 Focus 源码或正式数据库。

新增 Go／Python 测试覆盖：连续调用复用和总量上限、不同工作区替换、权限在池等待后撤销、未登记调用不能启动解释器、旧调用取消不误杀后继任务、运行中取消等待退出、worker 崩溃不重放、异常与输出超限、模块全局／cwd／环境／输出清理、线程／async 后台任务／同步函数遗留 event loop／退出钩子拒绝，以及寿命上限回收。成功的复用调用依靠可信工具协作契约，不提供任意 Python／native 代码沙箱或后代进程治理。

另修复截断 trace 诊断帧提前返回绕过逻辑输出上限的问题：实际 Go→Python 回归先复现 `OutputLimit=128` 却返回 4352 字节，再确认修复后正文受限，保留取消优先级。M1 代码保持原样并重跑 `go run ./cmd/lab`；其数字不作为本轮 pool 性能证据。

默认执行模式的完整共享运行时 [必须完成扫描负对照](../results/python-pool-negative-control-2026-10-28.json) 也重跑一轮：barrier 2002.36 ms、event 2018.95 ms，均完成相同扫描和产物，没有观察到纠偏收益。这只是兼容性回归，单轮不做统计推断，也不作为 pool 的性能对照。
